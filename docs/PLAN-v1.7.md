# v1.7 计划（内容扩张版）：从「小品」到「耐玩」

> **前置状态**：v1.6.0 已交付（纯单机打磨版，`mvn -o verify` 173 用例全绿）。骨架、元系统、手感、工程化均已就位。
> **唯一致命短板是内容量**：30 种卡（17 随从 / 8 法术 / 5 宠物）、标准牌堆 40 张，一局 8~15 回合就见底，
> 打十几局就会把每张牌认全。
>
> 本版只做一件事：**把卡池撑起来，并先拆掉挡住卡池扩张的三处天花板。**
>
> 配套：`docs/BACKLOG.md`（能力清单）、`docs/BALANCE.md`（数值规范）、`docs/dev-workflow.md`（流程与门禁）、
> `docs/CHANGELOG.md`（发布历史）。

## 0. 前提（不变）

① 简单小巧 ② 纯单机不联网 ③ 死守「卡牌对战」边界。
本版**不新增任何系统**，只做「扩容 + 拆天花板」。

## 1. 三处天花板（必须先拆，否则卡加不动）

### P0-1 · 松绑 `AssetsCoverageTest` 的卡数断言

**现状**：`src/test/java/org/example/card/ui/AssetsCoverageTest.java` 里
`assertEquals(30, cards.size())` 写死了卡库规模，同时又要求每张卡都有 `/images/cards/<id>.png`。
结果是**每加一张卡，构建必红**——与 README 承诺的「加新卡不用改代码」直接冲突。

**改法**：断言从「卡数必须等于 30」改为「**卡库里的每一张卡都必须有卡图**」（数量无关）。
卡库规模由 `CardDatabaseTest` 与 `BalanceCheckTest` 把关，不由资源覆盖测试把关。

**验收**：临时增删一张卡（验证后还原）不再需要改任何测试。

---

### P0-2 · 效果规格数据驱动化（本版唯一的代码工程）

**现状**：关键词是**固定机制**——`BATTLECRY` 永远等于「上场抽一张牌」，
`DEATHRATTLE` 永远等于「阵亡时对敌方英雄造成 2 点伤害」（见 `effect/KeywordTriggers.java`）。
于是带战吼的卡再多，战吼都一模一样，**内容多样性被封顶**。

**改法**：把效果从「关键词级」升级为「**卡级的效果规格**」，写在卡 JSON 里：

```json
{"id": "m18", "name": "……", "text": "战吼：打 2 点；亡语：抽一张牌",
 "attack": 2, "health": 3, "cost": 3, "keywords": ["BATTLECRY", "DEATHRATTLE"],
 "battlecry":   {"kind": "DAMAGE", "amount": 2},
 "deathrattle": {"kind": "DRAW",   "amount": 1}}
```

- `CardDatabase` 解析成效果描述（缺省时回退到关键词的默认规格，老卡零迁移）；
- `TriggerSystem` / `KeywordTriggers` 按描述派发，而不是按关键词写死；
- 关键词保留为「有该关键词 ⇒ 有对应规格」的**语义标签**，卡面徽章与 `BalanceCheck` 的计分口径照旧。

**首批支持的 `kind`**：

| kind | 语义 | 目标 |
|---|---|---|
| `DAMAGE` | 造成伤害 | 战吼 → 敌方英雄；亡语 → 敌方英雄 |
| `HEAL` | 回复生命 | 己方英雄 |
| `DRAW` | 抽一张牌 | 己方（走统一抽牌管线，满手烧牌） |

（`SUMMON_TOKEN`（召唤衍生物）留到下一批，需要先有衍生物卡表。）

**验收**：至少 3 张新卡的战吼/亡语**各不相同**，且全部由 JSON 驱动（不改代码）。

### P0-3 · 卡池 30 → 50~60 张

分两批，每批 10~15 张，按费用曲线铺（1~8 费）。每张卡必须同时满足：

1. **有明确用途与取舍**（不是按曲线铺白板）；
2. **落在香草公式容差内** —— `BalanceCheckTest.standardDeckPasses` 零告警；
3. **有卡图** —— 可先用程序化回退过渡，但要有图（P0-1 松绑后不再阻塞构建）。

## 2. 扩展包设计表（模板：落 JSON 之前先填这张表）

| id | 名称 | 类型 | 费用 | 身材 / 效果 | 关键词 | 定位 | 副作用 / 代价 | 卡图 |
|---|---|---|---|---|---|---|---|---|
| m18 | …… | 随从 | 3 | 2/3 | BATTLECRY | 中速补牌 | 身材偏小 | 待做 |
| s9 | …… | 法术 | 2 | 打 2 抽 1 | — | 节奏 | 费用偏高 | 待做 |

**设计要求**

- 每个费用档至少 2 张可选，避免费用曲线断层（构筑器有曲线图，断层会很明显）；
- 至少形成两种**可辨识的打法**（例：低费快攻 / 高费控制），让「构筑」真的有取舍；
- 单卡超模必须配对等副作用 —— 见 `docs/BALANCE.md` 的「出牌哲学」。

## 3. 验收与门禁（每批收口必跑）

| 门禁 | 命令 | 通过标准 |
|---|---|---|
| 编译 + 全量单测 | `mvn -o verify` | 全绿 |
| 整局冒烟 | `java -Dui.autoplay=10 -cp "target/classes:$(cat target/cp.txt)" org.example.card.ui.Main` | exit 0 |
| 数值体检 | `BalanceCheckTest.standardDeckPasses` | **零告警** |
| 天梯回归 | `AiLadderTest`（固定种子，可复现） | 先手胜率不显著恶化（基线见 `docs/BALANCE.md`） |
| 双主题截图 | `-Dui.screenshot` 暗 / 亮各一张 | 新卡卡面可读、不破版 |

**红灯停线**：任一门禁不过不合并。流程细节见 `docs/dev-workflow.md`。

## 4. 本版明确不做

新手引导、解锁/收集进度、AI 增强、卡牌编辑器、联机 —— 一律留到后续版本，
清单与裁定见 `docs/BACKLOG.md`。**本版只解决「内容量」这一个短板。**

## 5. 一句话

> 先把 `AssetsCoverageTest` 的卡数锁拆掉、把战吼/亡语变成数据驱动，卡池扩张就只剩「按设计表填 JSON + 出图」——
> 那时「慢慢填内容」才真正成立。顺序不能反：先拆天花板，再铺内容。
